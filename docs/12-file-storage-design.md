# 去除 SQLite：文件存储设计与实施计划

历史记录：其中的旧格式兼容、迁移流程和阻止启动策略已经取消，当前行为见 [非阻塞启动修复](16-startup-report.md)。

日期：2026-10-22。用户已确认去掉 SQLite，先更新设计再实施。本设计取代早期文档中 SQLite、WAL、事务表与数据库迁移方案；编辑、文件关联和自动保存的产品语义不变。

## 存储布局

沿用各系统标准应用数据目录，应用不再链接或运行 SQLite：

- `session.json`：带 `version: 1` 的提交清单，包含标签顺序、活动标签、编号、偏好及工作区文件引用。
- `workspaces/<UUID>-<SHA256>.json`：每个工作区的 UTF-8 JSON，含文本、语法范围及文件关联。内容寻址、不可变；只为变化的工作区写新文件。
- `backups/backup-*.json`：完整、独立可恢复的版本化快照，最多保留 3 份；最多每 60 秒一次，正常退出强制备份。
- `instance.lock`：原有单实例保护。
- `recovery/archive-*/`：恢复前保留原清单及工作区文件，不自动删除。

清单不存放文本，所有文本均为 JSON 字符串，不做换行或 Unicode 规范化。

## 一致性与错误处理

保存前验证完整模型。工作区新版本先在同目录临时文件写入、flush/sync，再原子发布；最后原子替换 `session.json` 作为唯一提交点。中途失败时旧清单仍指向完整旧版本。Unix 同步父目录；Windows 使用 tempfile 的平台原子替换，不声称 std 能同步目录或保证任何硬件断电场景。

清单提交成功后才更新“已保存”；备份失败单独提示。后台不引入异步数据库线程。保留 400ms 防抖、最长约 2 秒提交和 3 秒错误重试。正常退出保存并备份，不再有 WAL 检查点维护。清理只删除当前清单不再引用的已发布工作区版本，备份本身包含全部数据；清理失败按维护错误显示，不误报文本未提交。

启动验证格式版本、文件名、内容校验和、模型关系与偏好。损坏或引用丢失时先归档原文件，再尝试最新有效完整备份；无备份则保留原件并停止进入可编辑空白状态。未知新版本拒绝加载，不擅自恢复旧版本。缺失清单但存在工作区文件/备份时不作为首次启动。

## 旧版迁移

为彻底移除 Rust SQLite 依赖，迁移采用独立 Python 3 标准库脚本 `scripts/migrate-sqlite.py`，只读旧 SQLite（包含已提交 WAL），生成 `migration.json` 完整快照。脚本取得同一个实例锁，要求关闭旧应用；不修改或删除原库、WAL、备份。应用下次启动验证快照并提交为新格式，提交成功后留下已导入标记。正常运行不需要 Python。

只有旧数据库、尚无新格式时，应用明确显示迁移指引，绝不初始化空白覆盖旧数据。新格式一旦存在即优先使用，不反复导入。导入失败保留迁移快照和原数据库供重试。旧库损坏需先恢复旧备份或从旧版导出恢复 JSON；迁移脚本支持 schema 1/2，拒绝其他版本。

## 实施及验收

1. 替换独立持久化模块及集中路径，移除 rusqlite、表迁移、数据库恢复代码和锁文件中的依赖。
2. 保留现有 UI 错误/重试机制，替换数据库文案与路径显示；移除检查点行为。
3. 重写针对 SQL 触发器的失败注入测试，使用真实文件路径故障；增加提交中断、损坏/缺失引用、版本保护、备份、迁移及清理测试。
4. 更新原生持久化探针、Linux 启动验证、README 和依赖声明；实际运行 fmt/check/test/clippy、原生重启恢复及文件工作流。
5. 保留真实用户目录不动，不自动终止当前旧版应用。发布新包，并提供已验证的迁移命令。

此改造简化持久化与排查，不承诺明显降低图形渲染占用或启动内存。
