# 非阻塞启动修复

日期：2026-10-22。用户明确要求开发阶段不保留旧格式兼容，任何工作区读取错误都不能阻止编辑器运行。本记录覆盖早期文档中的兼容与启动阻塞策略。

## 改动

删除旧库检测、旧路径 API、迁移快照自动导入、迁移脚本/测试/原生探针及构建打包和 CI 的相应步骤。应用只处理 `session.json`、`workspaces/` 和自身 JSON 备份，不检查其他格式。源代码、脚本和 Cargo 依赖均已检查，不含数据库兼容分支。

`Store::open` 继续严格校验自身文件，保护损坏或未知版本数据；UI 不再用全屏启动错误替换编辑器。主工作区打开失败时，由独立持久化模块寻找可用恢复目录，编辑器继续显示标签、文本区和所有基本操作，并正常自动保存。路径依次为主目录追加 `.recovery`、用户缓存的隔离目录、系统临时稳定目录及最后的唯一目录，避免覆盖其他实例。前几项稳定目录可在后续启动中恢复内容。

顶部通知显示当前使用恢复工作区，详情显示原失败原因和实际保存位置；状态栏使用“已保存到恢复工作区”。主目录和恢复目录都受普通文件导出覆盖保护。所有本地写入位置都不可用时，保留可编辑内存状态，明确提示未落盘，允许导出或复制恢复 JSON；有内容时退出仍需处理未保存状态。

恢复工作区与主工作区分离，不自动合并；若主工作区后来恢复正常，应根据原提示目录手动保留或导出恢复内容。临时目录可能被系统清理，不应作为长期重要内容的唯一副本。

## 当前修复结果

已重新打包并打开 macOS 应用，确认原先报错的窗口退出，新版进程持续运行，真实标准数据目录生成 `session.json` 和工作区 JSON，并通过 SHA-256 校验。目录中的原有无关文件保持原样，不要求用户运行迁移命令。未终止健康且正在编辑的实例；只关闭了确认未持有工作区锁且没有成功创建清单的原报错窗口。

## 验证

macOS ARM64：94 项 Rust 测试通过，fmt、check（all-targets）、严格 clippy 与 release 打包通过。新增/修改用例验证：其他文件不阻止新 JSON 工作区；第二实例可以编辑、独立保存并重启恢复；无有效备份的损坏主清单不阻止编辑且原字节保留；数据目录被文件占用或主清单为较新版本时仍可输入并落盘到恢复目录。

Linux ARM64/X11：94 项 Rust 测试、fmt/check/clippy、实际应用启动、四套主题窗口、正常/异常恢复、文件工作流、真实 xclip 剪贴板及约 1MiB 编辑探针全部通过。Windows、Linux x86_64、Wayland 尚未实测。未制造真实磁盘耗尽，所有本地位置都不可写的分支以显式内存状态处理，不承诺无法落盘时仍能自动保存。
